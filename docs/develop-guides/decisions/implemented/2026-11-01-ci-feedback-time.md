# 缩短 CI 验证等待并恢复真实供应商探针

状态：implemented
类型：testing
Owner：.github/workflows/system-tests.yml

## 问题

前端完整测试逐文件串行执行，系统测试的检索与其他检查在同一 job 中串行；两者增加 PR 的反馈时间。完整测试集合、独立拓扑与失败传播必须保留。

手动真实供应商探针指定 self-hosted runner，环境准备脚本只允许临时托管执行器，因此探针即使有供应商密钥也不能进入测试。

## 决策

### 实现方案

`frontend/package.json` 以两个测试文件进程执行完整 Node 测试集合。使用 Vite 的测试继续使用原有测试宿主及独立临时缓存；不改变测试选择或断言。

`system-tests.yml` 复用原有两个隔离 Compose job。后台作业重建验证结束后，在该 job 的完整拓扑执行 Milvus 检索。另一 job 继续执行 Agent 生命周期和其余系统验证及其重放服务。环境准备脚本为每个 job 生成独立的临时加密密钥，供 API 与 worker 共同使用。最终汇总继续要求两个 job 成功；它检查 job 的状态，不检查成功 job 内 pytest 用例的 skip。

`real-provider-probe.yml` 使用临时托管执行器、container 沙盒及默认知识能力需要的 Compose 服务。探针仍只允许手动触发，并在缺少 `SILICONFLOW_API_KEY` 时失败；Cube 专项验证由已有独立探针负责。

## 替代方案

- 前端保持单进程：隔离开销低，但每个文件都在关键路径上等待。
- 前端使用四进程：本地更快，但单个重型测试进程的内存占用已达数 GB，执行器资源波动时风险较高。
- 将 Agent 生命周期也迁至后台 job：完整批次出现流式取消历史缺失，原位置保留该批次，等待缺陷独立排查。
- 新增系统测试 job：可进一步拆分，但需要额外构建和维护一整套拓扑；两个既有 job 已有明显的耗时差。
- 在同一拓扑并行运行所有系统测试：多个测试会重建服务或修改共享状态，不能保证隔离。
- 放宽 self-hosted 保护以运行真实供应商探针：会削弱对持久机器的保护；复用托管执行器更直接。

## 后果

系统测试仍运行原有集合，两个 job 分别持有数据库、对象存储、worker 和沙盒。`system-19.xml` 随其执行 job 上传到 `background-job-worker-path-junit`，而非原来的 `system-tests-junit`；仓库内没有按旧 artifact 位置读取它的消费者。仓库外精确依赖旧位置的消费者需要调整。

本地四核亲和基准中，前端串行、两进程和四进程分别约为 219、143 和 110 秒；三次均执行相同的 1007 个测试。两进程降低等待并控制资源使用，本地时间不能代替 GitHub 托管执行器的实测。供应商配额导致的 pytest skip 不是外部模型通过。

## 验证

- 前端串行、两进程和四进程各 1007 passed、0 skipped；逐项比较通过的测试名一致。独立 Compose 前端容器执行 lint、两进程完整 unit、类型检查与生产构建通过，1007 passed、0 skipped；测试后独占 Vite 临时缓存目录为空。人为失败的 Node 断言使两进程命令非零退出。
- 独立 Compose 拓扑按新顺序执行后台作业恢复、HTTP 与文档回滚、Milvus 检索和重解析；回读六份 JUnit 报告共 110 项，0 skipped、0 failure。随后执行的 Agent 生命周期整批为 44 passed、1 failed：流式取消时公开历史有时缺少已展示的文本。独立隔离拓扑针对同一用例重复 10 次，1 次失败；没有修改该断言或修复该缺陷。
- 托管环境和 workflow 接线测试执行真实环境准备脚本及 Compose 配置展开，验证两个进程收到相同加密密钥；负控覆盖检索入口、job 汇总、托管 runner、完整拓扑和供应商密钥入口。实际凭据准入 shell 在空密钥时失败。
- 真实供应商探针在另一隔离 Compose 拓扑中以本地 OpenAI 协议替身执行，原有探针用例通过并核对 SSE 与持久结果。未使用真实供应商密钥，不能证明外部供应商可用性或协议漂移。
- 后端容器 unit 为 3495 passed、125 skipped；容器不能覆盖的宿主配置测试另有 207 passed。工程契约检查及其单测、资源边界和 CI 汇总测试通过；测试规范的文档构建通过。

未在本地完整执行调整后的主系统 job；远端 CI 的实际耗时和真实供应商调用以对应运行结果为准。
