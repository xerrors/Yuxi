# 解析产物编辑先只放开待入库状态

状态：implemented
类型：feature
Owner：backend/package/yuxi/knowledge/base.py

## 问题

解析完成后、入库前的人工复核目前只能靠删掉重传再解析。允许直接编辑解析产物能省掉这条链路，但「编辑解析产物」包含两种复杂度差异很大的形态：

- 改一个**还没有索引**的文件：产物对象就是唯一内容，覆盖即发布；
- 改一个**已经入库**的文件：必须同步清理 PostgreSQL 分块、Milvus 向量与图谱，并保证清理与内容发布不会留下半成品状态。

把两者放进同一个同步接口，会出现「先覆盖 MinIO 产物 → 再清索引 → 最后改状态」的时序：清理失败或状态 CAS 落空时接口返回 500/409，但新产物已经成为持久内容，文件仍是 `indexed` 且向量是旧的。此外，两个并发的产物编辑也无法由 `parsed → parsed` 的状态 CAS 拦住——两边读到与写回的状态都成立。

## 决策

第一阶段只放开 `parsed`：`EDITABLE_MARKDOWN_STATUSES = {FileStatus.PARSED}`，保存覆盖确定性路径 `{kb_id}/parsed/{file_id}.md` 并保持状态不变，用户继续走既有「入库」。已入库内容的编辑不在本接口范围内。

- **发布时点**：parsed 文件没有派生索引，产物对象就是权威内容，覆盖即发布，因此不需要「草稿 / 权威版本切换」。这条判断随第二阶段重新评估。
- **并发**：把期望版本做成落库条件。`revision` 是文件行的 `updated_at`（随 GET 内容返回，PUT 原样回传），保存时与允许状态一起组成**同一条 UPDATE 的等值条件**（`update_fields_if_status` 的 `expected_updated_at`）。因为任何对文件的写入都会推进 `updated_at`，所以两个并发保存只有一条能命中，另一条返回 409；编辑期间解析/入库任务推进状态或版本同样让条件落空。校验与发布因此是一个原子步骤。
- **顺序是先条件更新再覆盖产物**：条件落空时产物尚未写入，不会出现「接口失败但新内容已持久化」。
- **失败面**：空内容、缺修订或修订非法、文件夹、无产物、超出体积上限都在落库与落盘之前拒绝。保存不再读取旧产物对象（期望版本来自文件行），因此对象缺失不会被误判为可编辑。

## 替代方案

- **同一接口同时支持 parsed 与已入库编辑**：清理流程应与既有「重新入库」Durable Task 合一（由任务取得 ownership 后再切换权威内容），而不是在同步接口里另实现一套。已入库编辑进入第二阶段。
- **只靠状态 CAS 做并发控制**：对两个 parsed 编辑者无效（状态相同），会静默后写覆盖前写。
- **读产物算 sha256 做乐观并发**（本 PR 实现过程中的第一版）：比对「客户端读到的产物」与「保存时的产物」。它是**非原子的读**——校验与落库之间隔着对象读写，两个并发请求会双双通过校验、双双写入，后写覆盖先写（用并发探针复现过）。因此改为把期望版本放进 UPDATE 的 WHERE。
- **接受后写覆盖、只记录为已知限制**：实现更小，但用户已输入的编辑会无提示丢失，因此改为把期望版本做成落库条件。
- **抢占式 CAS / lease**：编辑不创建任务，进程崩溃会让文件永久卡在中间态，而 `fail_task_processing_in_session` 只收敛有 task 归属的状态，因此不采用。

## 后果

- 已入库文件不再提供编辑入口，其内容修正回到「重新入库」链路（该链路只按当前产物重建索引，不改内容）。
- 产物被第三方改动（另一个编辑者、重新解析覆盖）时保存返回 409，用户需重新打开编辑；保存成功后响应回传新的 `revision`，避免用户连续编辑时被自己上一次的保存判为冲突。
- 没有跨进程互斥。残留窗口是「条件更新成功、写对象失败」：状态与内容仍是旧的一对，自洽，但行的版本已经推进，客户端手里的 `revision` 随之过期——它下一次保存会拿到 409 并需要重新打开编辑。反过来（写成功、条件落空）在本顺序下不会出现。
- 期望版本用时间戳：两条写入落在同一微秒的理论碰撞窗口存在（每次条件更新都要走一次数据库往返，实际不可达）；换成计数器列可以彻底消除，但那需要新列与历史数据回填。
- 只读连接器由 HTTP 层的 `_ensure_database_supports_documents` 拦下，权限由 `require_knowledge_base_manage` 收口。
