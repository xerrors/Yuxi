# 解析产物编辑先只放开待入库状态

状态：implemented
类型：feature
Owner：backend/package/yuxi/knowledge/base.py

## 问题

解析完成后、入库前的人工复核目前只能靠删掉重传再解析。允许直接编辑解析产物能省掉这条链路，但「编辑解析产物」包含两种复杂度差异很大的形态：

- 改一个**还没有索引**的文件：产物对象就是唯一内容，覆盖即发布；
- 改一个**已经入库**的文件：必须同步清理 PostgreSQL 分块、Milvus 向量与图谱，并保证清理与内容发布不会留下半成品状态。

把两者放进同一个同步接口，会出现「先覆盖 MinIO 产物 → 再清索引 → 最后改状态」的时序：清理失败或状态 CAS 落空时接口返回 500/409，但新产物已经成为持久内容，文件仍是 `indexed` 且向量是旧的。此外，两个并发的产物编辑也无法由 `parsed → parsed` 的状态 CAS 拦住——两边读到与写回的状态都成立。

## 决策

第一阶段只放开 `parsed`：`EDITABLE_MARKDOWN_STATUSES = {FileStatus.PARSED}`，保存后状态保持不变，用户继续走既有「入库」。已入库内容的编辑不在本接口范围内。

- **发布时点**：编辑先写**内容寻址的新对象**（`{kb_id}/parsed/{file_id}.{hash16}.md`），再在**一条**条件更新里把 `markdown_file` 切过去。于是「引用即内容身份」成立——任何读者（含入库）读到的对象，由它读到的那一行 `markdown_file` 唯一确定，不会读到被覆盖一半的内容，也不会出现「产物已换、行还指旧对象」。parsed 没有派生索引，所以不需要草稿态；但「覆盖即发布」这个判断不成立：入库任务与本接口并发时，覆盖写会让它读到旧内容。
- **并发**：把期望版本做成落库条件。`revision` 是文件行的 `updated_at`（随 GET 内容返回，PUT 原样回传），保存时与允许状态一起组成**同一条 UPDATE 的等值条件**（`update_fields_if_status` 的 `expected_updated_at`），引用切换（`markdown_file`）与它同批下发。因为任何对文件的写入都会推进 `updated_at`，所以两个并发保存只有一条能命中，另一条返回 409。
- **顺序是先写新对象、再条件更新**（与 `parse_file` 一致）：反过来会在条件成功后、对象写入前的窗口里让入库认领通过并读到旧内容，形成「产物新、分块与向量旧」。入库读的是它认领 CAS 返回的那一行，因此两侧由行锁串行——本接口先命中则引用已切换、入库读到新内容；入库先命中则状态变 `indexing`、本接口条件落空。任一顺序下，入库建索引所用的内容都与该行最终的 `markdown_file` 一致。
- **失败面**：空内容、缺修订或修订非法、文件夹、无产物、超出体积上限都在落库与落盘之前拒绝。保存不再读取旧产物对象（期望版本来自文件行），因此对象缺失不会被误判为可编辑。条件落空时新对象已落盘但无人引用，**刻意不删**（理由见「替代方案」）；代价是一次失败保存留下一个孤儿，由删除文件时的前缀清理收敛。

## 替代方案

- **同一接口同时支持 parsed 与已入库编辑**：清理流程应与既有「重新入库」Durable Task 合一（由任务取得 ownership 后再切换权威内容），而不是在同步接口里另实现一套。已入库编辑进入第二阶段。
- **只靠状态 CAS 做并发控制**：对两个 parsed 编辑者无效（状态相同），会静默后写覆盖前写。
- **读产物算 sha256 做乐观并发**（本 PR 实现过程中的第一版）：比对「客户端读到的产物」与「保存时的产物」。它是**非原子的读**——校验与落库之间隔着对象读写，两个并发请求会双双通过校验、双双写入，后写覆盖先写（用并发探针复现过）。因此改为把期望版本放进 UPDATE 的 WHERE。
- **接受后写覆盖、只记录为已知限制**：实现更小，但用户已输入的编辑会无提示丢失，因此改为把期望版本做成落库条件。
- **条件落空时删除刚写的新对象**：被否。内容寻址名是内容的纯函数，两个编辑者提交**同一份文本**时（同一处修正、脚本重放、超时重试），输家写的对象与赢家已切换引用的是同一个——删它会让行指向不存在的产物（下载与预览失败、入库转 `error_parsing`）。改为接受孤儿，由删除文件时的前缀清理收敛。
- **给新对象名加随机后缀以允许删除**：被否。那样会失去「同内容幂等覆盖」——同一份内容每提交一次就多一个对象，孤儿量随提交次数线性增长；把「会不会误删活对象」换成「孤儿增长」，取舍上更差。
- **抢占式 CAS / lease**：编辑不创建任务，进程崩溃会让文件永久卡在中间态，而 `fail_task_processing_in_session` 只收敛有 task 归属的状态，因此不采用。

## 后果

- 已入库文件不再提供编辑入口，其内容修正回到「重新入库」链路（该链路只按当前产物重建索引，不改内容）。
- 产物被第三方改动（另一个编辑者、重新解析覆盖）时保存返回 409，用户需重新打开编辑；保存成功后响应回传新的 `revision`，避免用户连续编辑时被自己上一次的保存判为冲突。
- 没有跨进程互斥。残留面是「条件落空、新对象已落盘」：那个对象不被任何行引用（孤儿），内容与行仍是一致的一对，客户端按 409 提示重新打开编辑即可；孤儿由删除文件时的前缀清理（`_delete_parsed_objects`）收敛。反过来（引用已切换但对象不存在）在本顺序下不会出现——CAS 成功即意味着对象此前已写入。
- 文件夹删除路径不经过 HTTP 层的对象清理，因此 `delete_folder` 对每个子文件同样调用 `_delete_parsed_objects`，否则编辑过的子文件会留下永久孤儿。
- 产物对象在前缀 `{kb_id}/parsed/{file_id}.` 下可能存在多个（解析产出的确定性名 + 历次编辑的内容寻址名）。删除按该前缀清理，点号是必要锚点：不带时 `file_id` 互为前缀的文档（`abc` 与 `abcdef`）会被误删。
- 删除文件时**先删行、再清理对象**，单条与批量两个入口都是这个顺序。行先消失，任何 CAS 成功的编辑其对象都写在删行之前，最坏只是多删一个对象；`delete_file` 失败则行与对象都还在，不会出现半删状态。反过来（先列举清对象、再删行）在两步之间提交的编辑会让行指向已经被删掉的对象，预览与下载失败、入库转 `error_parsing`。孤儿窗口并没有消失（编辑在删行前读到版本、对象写在列举之后仍会留下一个），但它比旧顺序窄，且不再产生悬空引用。
- 期望版本用时间戳：两条写入落在同一微秒的理论碰撞窗口存在（每次条件更新都要走一次数据库往返，实际不可达）；换成计数器列可以彻底消除，但那需要新列与历史数据回填。
- 只读连接器由 HTTP 层的 `_ensure_database_supports_documents` 拦下，权限由 `require_knowledge_base_manage` 收口。
- 前端把「保存」的上下文也用请求序号框住：关闭弹窗或切换到另一份文档即作废在飞的保存响应，避免旧响应把新文档的 meta、修订或提示改掉；同时解除「保存中」，否则那次保存之后编辑框会一直是禁用状态。保存期间 textarea 与保存按钮都由 `AgentFilePreview` 的 `saving` 禁用，因此不存在「等待期间继续输入被当成已保存内容」的窗口。保存期间关闭弹窗不再弹「放弃未保存的修改」——服务端已经在写，那句话与事实相反。
- 编辑是**独占态**：草稿存在 `AgentFilePreview` 的局部状态里，而 Markdown 分支是 `v-if` 渲染的，切到「源文件 / Chunks」会让它连同草稿一起被卸载，且切换本身没有确认步骤。因此编辑期间禁用视图切换，与「保存期间禁用输入」同一种收敛方式。
