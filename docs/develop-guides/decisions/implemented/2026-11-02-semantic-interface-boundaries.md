# 接口复用的语义边界检查

状态：implemented
类型：process
Owner：docs/develop-guides/spec-loop.md

## 问题

按目录分层和声明语义 Owner，仍不足以判断一条新增条件是否属于通用接口。调用者的展示规则、特定工具结果解释或当前执行上下文可能进入共享能力，使其他入口或恢复路径得到与接口承诺不同的结果。

目标是让贡献者在复用接口、增加条件分支时识别事实归属、接口承诺和调用者策略，并用受影响路径的契约证据支持 Review。不进行全仓代码重构，不新增中央清单或静态语义判定器。

## 决策

### 实现方案

根 [AGENTS.md](https://github.com/xerrors/Yuxi/blob/main/AGENTS.md#任务与决策) 拥有设计规则的触发入口；[Spec Loop](../../spec-loop.md#接口复用与语义边界) 的权威重建阶段拥有完整的接口边界检查，独立 Review 阶段引用该检查。[测试规范](../../testing-guidelines.md#跨入口与恢复的契约验证) 拥有跨入口与恢复场景的选例方法。[贡献指南](../../contributing.md#_5-提交前-review)的 Review 入口链接同一检查，避免人类贡献者遗漏。各子树指令、架构地图和工程信任系统保留现有职责，不复制完整规则。

检查围绕当前接口和真实消费者展开：先写事实 Owner 与承诺，再区分展示、工具协议和执行差异，沿真实注册、调用及恢复路径核对。调用者策略在已有适配或投影处完成；共同约束仍由共同能力维护，显式适配不要求为每个入口新建一层。

## 替代方案

- 只增加“单一职责”原则：简短，但缺少触发时机、调用路径检查和 Review 拒绝条件。
- 在各子树、架构和 PR 模板复制完整规则：增加同步成本，不能改善唯一事实归属。
- 静态搜索工具名、页面名或条件分支并阻断：无法区分合理协议适配与职责泄漏，易产生误报。
- 扩展现有设计、测试与 Review 入口：采用，规则有唯一解释位置并进入现有工作流。

实际执行：

```bash
python3 scripts/ci/verify_engineering_contracts.py
python3 -m unittest scripts.ci.test_verify_engineering_contracts
(cd docs && pnpm run build)
git diff --check
```

工程契约检查通过，校验器 unit 56 项通过；文档构建通过，保留大 chunk 提示。生成 HTML 的“接口复用与语义边界”和“跨入口与恢复的契约验证”锚点经回读确认存在。独立 Reviewer 审查完整规范 diff、决策及实际证据，无阻塞发现。

产品 unit、integration、E2E 与浏览器验证为 `Not run`：变更仅涉及规范文档，不改变产品行为。此次文档与 Review 证据不证明全仓实现已经符合新增规则，也不证明未来 Reviewer 必然能识别所有职责泄漏。

## 后果

语义归属不能由关键词 gate 证明，仍依赖 Reviewer 检查真实需求与消费者。场景按受影响契约选择，避免将举例变成所有变更的固定测试笛卡尔积。文档验证不证明现有产品实现已完成边界审计。
