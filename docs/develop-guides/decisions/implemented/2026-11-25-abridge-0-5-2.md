# aBridge 0.5.2 发布镜像与启动

状态：implemented
类型：architecture
Owner：docker-compose.abridge.yml

## 问题

Compose 的 0.4.13 基线早于 Cube 的个人和 APP 浏览器登记协议，启用登记依赖另外构建的候选镜像。

## 决策

### 实现方案

Compose 固定 0.5.2 官方多架构镜像摘要，沿用镜像的 Server 启动入口和健康检查时序。aBridge 拥有 SQLite、启动校验和设备授权。Yuxi 继续通过 OIDC 和短期委托接入。新建 Cube 模板使用同版本正式浏览器发行物。镜像固定是[接入配置与协议归属](2026-11-17-abridge-simplification.md)中的部署决定的延续。

`operation_cancel` 沿用 `operation_status` 的回执展示，区分待确认的取消请求、取消完成以及结果未知。历史 `command_cancel` 回执继续沿用既有展示。

## 替代方案

- 保留旧默认镜像，通过覆盖文件启动候选构建。这要求部署方自行匹配 Server 和浏览器发行物。
- 自动修改旧 SQLite 数据。aBridge 0.5.2 不提供 schema 3 升级器，Yuxi 不拥有旧数据转换契约。

## 后果

0.4.13 默认数据库为 schema 3。保留数据需在备份副本中验证离线转换，允许重新登记的部署可使用新卷。兼容的 schema 6 部署可保留现有卷和凭据。Server 重启期间设备需要重新连接。[启动与升级步骤](../../../advanced/abridge.md)

## 验证

- 开发与生产 Compose 以空卷启动同一个发布镜像，回读 `/health` 的版本。使用开发拓扑以运行数据库的 SQLite 备份副本启动，核对数据库完整性及设备登记。将测试副本的 schema 改为 3 后，发布镜像拒绝启动。
- 使用从发布镜像提取的 Server，在隔离 PostgreSQL、Redis 和真实 HTTP 上运行 `test_abridge_devices.py` 与 `test_abridge_delegation.py`。7 项通过，覆盖 OIDC、个人设备权限隔离、撤销和个人浏览器登记。
- 运行实例切换前后回读设备、凭据及个人和 APP 浏览器登记，SQLite 完整性和登记一致。正式浏览器发行物通过 Release SHA-256 校验。已有来宾客户端保持原有安装。
- 工具卡单测和浏览器用例检查取消请求、取消完成及结果未知的展示，确保已请求取消时仅显示请求状态。
