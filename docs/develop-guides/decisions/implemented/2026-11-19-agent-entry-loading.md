# 对话首屏、历史读取与侧栏刷新

状态：implemented
类型：architecture
Owner：frontend/src/app/router/index.js

## 问题

首页进入对话时，开发服务会传输尚未使用的排版、图表和预览依赖。旧对话首读可能从会话和最近轮次重复取得同一批消息。侧栏每 12 秒读取普通会话首页和置顶页，列表稳定时仍会下载相同正文。

## 决策

### 实现方案

- 路由在下载受保护页面前识别访客并保存返回地址，账户恢复、角色校验和草稿交接沿用现有流程。空白对话直接挂载时间线和输入框。答复先显示原文，Markdown 就绪后替换，排版加载失败时保留可读原文。预览、来源、调试面板、图表和代码高亮按实际使用加载。DiceBear 风格等首次使用再构造，文件图标使用静态资源 URL。
- Vite 只压缩开发模块响应，源码保留映射，API 和 SSE 沿用现有代理。模型菜单按需加载可选展示数据，目录可在元数据返回前搜索和选择。虚拟模块异步读取锁定快照，并省去生成数据的逐字段映射。
- Session runtime 的普通历史读取和上翻每批最多三页，每页 100 条。最近轮次已结束时，首读只补会话窗口缺少的轮次尾页，正式结果取自 Turn 详情。会话和轮次各用自己的游标。首读失败或执行变化时重新读会话窗口，继续跨过断点直到接回旧窗口。已完整读到终态的会话遇到迟到协作摘要时核对持久详情，避免重复完成。等待审批和 SSE 终态仍由运行恢复入口处理。重新打开旧对话时刷新评价。
- ThreadTimeline 在可见页面距顶部 600px 内向上滚动时加载旧页。首读未就绪、已有请求在途、页面隐藏、读完历史或前次读取失败时停止自动追加，失败后由原入口手动重试。追加期间停用原生滚动锚定，以可见消息的稳定 key 恢复阅读位置。continuation 重挂载后按同一 key 查找，找不到时按高度差补偿。
- 布局负责初次加载侧栏。会话路由按用户与 APP 权限查询分页，再根据完整响应生成 ETag。客户端按请求地址和身份保存普通首页及置顶页，携带对应 `If-None-Match`。收到空正文 `304` 时复用该页，换账号时清除快照。协议由[公开 Session API](../../../advanced/agents-public-api.md)维护。

## 替代方案

- 预取整个工作区会提前传输访客与空白对话用不到的资源。全局关闭 source map 会影响源码调试，压缩本身也无法减少解析成本。
- 只扩大每次读取窗口仍需反复点击，提高公开分页上限会扩大所有客户端的响应预算。一次加载全部历史会增加首屏等待和 DOM 开销。按时间缓存会话或用消息组顶部作锚点，可能分别读到旧状态或在同一 Run 内跳动。
- 专门的轮询摘要接口需要维护第二份读取契约。按账号维护变更版本会让所有影响列表的写入共同承担版本更新。

## 后果

首次用到排版和预览时会发起额外模块请求。历史列表的分页与锚点由阅读视图负责，模型上下文和公开内容分页契约保持原样。侧栏仍每 12 秒刷新已加载条目的状态和展示字段，首次加载与手动刷新负责列表成员及分页。稳定页省去正文传输和 JSON 解析，服务端仍读取同一分页。

冷缓存 5173 测量中，首页到空白对话的请求从 392 降至 294，传输量由 47.88 MiB 降至约 7 MiB。访客进入登录只增加 6 个请求。锁定的模型展示快照由 6,430,854 字节缩小到 gzip 134,396 字节或 Brotli 119,916 字节。

禁用 HTTP 缓存时，普通页依次返回 200、304、200、304，置顶页依次返回 200、304、304、304。另一客户端改名后下一轮更新侧栏，间隔约 12 秒。历史页面回放 950 条记录，普通上翻及同 Run 内追加的阅读锚点偏移均小于 1px。
