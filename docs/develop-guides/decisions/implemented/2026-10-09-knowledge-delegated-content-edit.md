# 知识库普通成员的授权访问与内容维护

状态：implemented
类型：feature
Owner：backend/package/yuxi/permissions/resource_permission.py

## 问题

普通成员被加入知识库共享管理范围后，仍看不到知识库页面，后端角色上限与管理员依赖也阻止访问。团队需要让成员维护获授权知识库内的文档，同时由管理员负责知识库配置与授权。相关上游功能建议见 [Issue #1094](https://github.com/xerrors/Yuxi/issues/1094)。

## 决策

复用 version 2 的读取和管理范围，不新增权限枚举或数据库结构。命中管理范围的普通成员获得文档及文件夹维护能力；知识库配置、共享权限、连接凭据、整库删除、图谱和评估管理仍要求管理员角色及该库管理权限。读取范围允许普通成员查看该库文档与现有读取功能。创建知识库和全局管理功能仍由管理员执行。

### 实现方案

资源权限解析拥有单库范围判断，FastAPI 依赖拥有操作级授权，Manager 与 HTTP 响应拥有过滤与凭据脱敏。响应区分 `can_edit_documents` 与 `can_manage`，前端按这两个能力展示操作；路由只要求登录，单库授权由后端裁决。上传和工作区导入要求普通成员提供已授权的知识库；文档提交校验对象属于目标库，不能引用另一库的原始或预处理对象。前端切换账户或目标库、权限请求失败时清理旧库状态与弹窗载荷，迟到响应不能覆盖当前会话。

非整库管理者的响应递归移除配置中的凭据及任意模型认证请求头，保留模型 token 预算和文档分块参数。可访问摘要始终脱敏；管理员且具有该库管理权限时，详情和图谱状态保留可编辑配置。脱敏生成副本，持久配置与模型运行参数保持原值。

文件仓储拥有跨库文件 ID 隔离。新文件 ID 使用现有短随机值；upsert 命中其他知识库的记录时抛出 `ValueError`，原记录不变。ID 算法和数据库结构保持现状，碰撞产生可观察的导入失败，调用方可以重试。

文档删除的存储清理拥有原件归属判断：只有 documents bucket 内当前库前缀的对象可以删除。管理员或历史跨库引用不赋予原件删除所有权，删除引用记录时保留外库原件，继续清理本库派生物与记录。这一归属约束同时适用于管理员和普通编辑成员。

任务中心和网页 URL 导入保持管理员能力，普通成员通过文档状态查看解析和索引结果。URL 抓取授权、整库所有者转移、新角色、权限迁移和任务授权体系超出文档委托范围。

## 替代方案

- 将成员升级为管理员：增加系统管理能力，超出文档维护任务。
- 仅开放菜单：路由和 API 仍拒绝授权用户，不能完成维护流程。
- 普通成员获得完整管理能力：共享配置、连接凭据与整库删除的权限范围超过团队当前需求。
- 新增独立编辑权限等级和共享字段：需要迁移与更多兼容逻辑；第一版复用已有授权意图，在操作边界区分角色。

## 后果

已有管理范围立即授予其中普通成员内容维护能力，包括全局或部门范围；上线前管理员需要确认现有范围确实表达编辑授权。文件删除属于内容维护授权，整库删除仍由管理员执行。解析和索引沿用后台任务，普通成员在文件列表查看最终状态。权限字段和数据库结构无需迁移。

普通文件夹上传使用叶子文件名作为 multipart 名称，通过既有 `source_paths` 保留目录结构，避免目录路径进入原文件上传名称。管理员原有上传流程保持可用。
