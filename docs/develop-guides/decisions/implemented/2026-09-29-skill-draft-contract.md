# Skill 安装草稿的可确认条目

状态：implemented
类型：architecture
Owner：backend/package/yuxi/services/skills/draft.py

## 问题

安装草稿的 `items` 曾同时包含有效包快照和远程拉取失败结果。个人与共享确认各自解释松散字典中的 `success`、slug 和目录路径；按 slug 选择时，重复条目也没有明确身份。

## 决策

### 实现方案

`services/skills/draft.py` 拥有上传和远程安装草稿的创建、加载、授权、条目选择、消费及删除。元数据 `items` 只包含已解析的包快照，获取或解析失败保存在 `failures`。共享授权选项由 HTTP 响应适配层装配，不进入草稿。草稿加载校验期限、操作者、来源、唯一 slug 与路径，向目标来源返回具名条目。

`remote.py` 拥有远程发现与目录下载；获取结果明确区分 `DownloadedSkill` 与 `SkillDownloadFailure`，下载完成不代表包格式有效。个人 service 同时拥有草稿确认和 Agent 直接安装；工具仅提取运行上下文并装配 ToolMessage，直接安装无需创建持久草稿。共享 service 在确认时分配 slug 并提交文件和索引。两个安装执行边界均重新解析复制后的包并核对草稿 slug。

页面保留失败条目对应草稿用于重试，用户结束流程时清理剩余草稿。重试按实际可复用失败条目选择路径；草稿只剩用户移除的条目时，清理旧草稿并重新获取远程失败项，不把已移除项重新加入安装。确认后只消费成功条目，保留失败和未选条目的快照及原有效期；元数据以临时文件替换发布，最后一个可安装条目消费后删除草稿。此契约支持正常请求完成后的部分失败重试，不承诺并发确认或进程崩溃后的恰好一次安装。个人安装已成功但草稿消费失败时，重试仍遵循个人同名拒绝规则。

上传与远程草稿共用元数据写入函数，来源入口只负责获取和暂存条目。ZIP 从上传字节直接解压；远程下载以请求位置保存逐项结果，显式在获取失败或沙盒清理失败时释放宿主临时目录，成功后由调用方持有。组合查询直接以 slug 合并共享和个人结果。

## 替代方案

- 保持成功与失败混合并在两个确认函数中重复判断：改动少，但草稿始终没有可执行契约。
- 引入跨个人与共享来源的通用安装状态机：能统一调用形状，却会混淆文件系统和数据库的不同发布规则。
- 改为公开 item ID 选择协议：身份最明确，但当前草稿可直接保证 slug 唯一，立即修改 HTTP 契约没有必要。

## 后果

草稿、包获取和目标安装各自拥有清晰边界；个人和共享保留各自发布规则。`prepare.py` 与旧准备函数移除，不提供转发兼容层。个人与共享组合查询归属 `catalog.py`。运行时先扫描个人来源，再锁定未被个人覆盖的已选共享包和依赖。显式选择的个人覆盖版本仍可按配置预加载，自动加入的个人包不扩大预加载范围。
