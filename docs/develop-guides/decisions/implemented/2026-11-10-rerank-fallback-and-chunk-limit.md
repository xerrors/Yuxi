# 重排失败占位与块数上限

状态：implemented
类型：bug-fix
Owner：backend/yuxi/modules/models/rerank.py

## 问题

一批重排失败时，`acompute_score` 用 0.5 占住每个文档的槽位，再与成功分数一起做 sigmoid。sigmoid(0.5) 约为 0.622，会排在真实低分之前。与此同时，`OpenAIReranker._build_payload` 把 `max_length`（默认 512，含义是文本长度）写入 `max_chunks_per_doc`。Dashscope 忽略该参数。调用方和测试都没有独立的每文档块数配置。索引对齐的其余契约见 [重排响应保持输入文档索引对应](2026-09-12-rerank-response-alignment.md)。

## 决策

### 实现方案

失败批仍为该批每个文档写入一个占位分，后面批次的分数保持原下标。占位的原始分是负无穷，并与成功分数走同一条 sigmoid；归一化后它低于任何不会下溢到 0 的有限真实分，未归一化时低于任何有限真实分。

OpenAI 兼容请求只发送模型、查询和文档。`max_length` 继续留在评分入口上，供已有调用方传入，但不再写入 `max_chunks_per_doc`。仓库里没有独立块数配置，因此默认请求不带 512，也不新增配置项。Dashscope 仍只按文档数要求 `top_n`。Milvus 继续按返回列表的位置写回分数，排序实现不变。

## 替代方案

- 继续使用 0.5：槽位对齐，但归一化后会盖过较低的真实分。
- 失败批直接缩短列表：破坏与输入文档等长的位置契约。
- 在 sigmoid 之后单独写一个负数：占位分不再和成功分使用同一归一化。
- 把 512 改成另一个默认块数：仍然把长度参数误当成块数。

## 后果

失败文档在与成功文档一起排序时落在真实分数之后；极端负的有限分数经 sigmoid 下溢到 0 时，可能与占位分的 0 并列。提供者不再收到把 512 当作每文档块数的请求，未配置块数上限时使用提供者自己的默认值。部分响应、非法索引和无效分数仍使整批失败，并走上述占位。

## 验证

`backend/test/unit/models/test_rerank.py` 用真实的 OpenAI 与 Dashscope 适配器检查：失败批占住原槽位，后续文档分数不错位，占位分低于同列表中的有限真实分；默认请求和显式 `max_length` 都不包含 `max_chunks_per_doc`。
